# Engineering workflow

Follow applicable instructions from the project you are working in. Read its existing project guidance and use its code, manifests, and CI to discover checks. For an investigation, return findings unless edits are requested. For a standalone review request, coordinate an [adversarial review](adversarial-review.md). If assigned as a reviewer, use the [reviewer brief](reviewer.md) and return your observations.

## Deliver the task

For a long-running task or requested handoff, [start a run record](resume.md#start-and-checkpoint) before implementation or dispatch. Use [active supervision](supervision.md) when an unattended run has in-flight work or is waiting on a signal that can advance it. [Resume from the record](resume.md#resume-from-a-fresh-session) before continuing inherited work. When delegating, use the [delegation playbook](worker.md) to assign work and [account for every required slice](worker.md#account-for-every-required-slice).

1. Turn the request into observable acceptance criteria. Inspect the current code, callers, tests, CI, and existing changes. Apply [design before coding](design.md) to risky changes before implementation edits, including scaffolding. Own reversible decisions. When a product tradeoff, missing access, or delivery authority needs the user, ask a focused question with a recommendation and continue unrelated work.
2. Discover setup and checks from the code, manifests, and CI. For a new project, build a first runnable slice and prove one real flow with test data. Record useful project facts in existing guidance. Find or establish a [repeatable verification recipe](verification.md) for behavior that needs runtime proof. Isolate concurrent or unattended work in separate worktrees or checkouts.
3. For bugs, reproduce the failure on the base when feasible and fix the root cause. For features, identify the affected data and callers. For refactors, capture a behavior baseline. Make the smallest coherent change, preserve existing contracts, and add behavior tests where they catch a meaningful regression. For a phased change, [verify each phase](design.md#plan-and-verify-phases) before starting work that depends on it. Checkpoint each verified phase when keeping a run record.
4. [Prepare changed code for review](adversarial-review.md#prepare-the-candidate) before final verification. Count applicable post-pass checks toward final verification. For changes to product behavior or verification prerequisites, use the project's [verification map](verification.md#build-a-verification-map) when present to select affected flows. Include changes to saved checks, setup, drivers, commands, and fixtures. Run their recipes through the real entry points. For risky changes, run the [blast-radius probes](blast-radius.md#try-to-disprove-it) on the prepared candidate. Run other required checks. Apply the [required-check gate](verification.md#protect-required-checks) to PRs before relying on changed checks. When an authorized change establishes or repairs a recipe, save it only after an end-to-end run succeeds. Refresh affected map entries when authorized and report stale checks separately from product failures. Record the candidate, commands, expected and observed results, and any missing evidence. Use comparable inputs for before-and-after checks. For model behavior, use representative fixtures and record settings that affect the result. Keep secrets and scratch artifacts out of the candidate.
5. When a change alters reusable skill behavior, [evaluate it blind](learning.md#evaluate-a-skill-change-blind) against the prior instructions and record the result or missing evidence. Run the [adversarial review panel](adversarial-review.md) on the verified candidate. For authorization changes, production data migrations, irreversible external operations, and other project-marked high risks, assign one reviewer to focus on that risk. Fix confirmed blockers, prepare the revised candidate, then rerun affected checks and review it. Stop repeating an unsuccessful step when there's no new change or evidence.

## PR and handoff

Use the [orchestration playbook](orchestration.md) for queues, dependent stacks, and resumed PR runs. Its [merge gate](orchestration.md#merge-gate) also applies to a single PR.

When authorized, commit only intended changes, push the task branch, and open or update its PR. Open in draft if the readiness gate has yet to pass. Include the goal, candidate, commands and observed results, reviewer verdict, independent live rerun evidence when required, and open findings. Follow [PR and CI triage](pr-triage.md) through the requested endpoint and fix confirmed in-scope failures.

Mark the candidate ready when the required checks pass and the [required-check gate](verification.md#protect-required-checks) is satisfied, any [required blast-radius evidence](blast-radius.md#use-the-result-for-delivery) is current and supports the safety assumptions, [all slices required for readiness](worker.md#account-for-every-required-slice) have acceptable evidence, and the adversarial review returns `PASS` on the current candidate. For code changes, confirm that verdict followed applicable [pre-review preparation](adversarial-review.md#prepare-the-candidate). For a behavior-changing PR, follow the [independent live rerun and readiness rules](adversarial-review.md#independent-live-rerun) before opening it as ready or marking it ready. Refresh affected evidence and review after the candidate or tested base changes. For unattended runs, use the [audited handoff](handoff.md) when returning control and keep routine results in the run record. For other work, report remaining blockers or decisions. If the run surfaced a durable lesson, use [Reflect](learning.md#reflect) and keep it in the record when using an audited handoff. Commit, push, merge, and deploy within the user's authorized scope.
