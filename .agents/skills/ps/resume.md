# Checkpoint and resume long-running work

Use this playbook for unattended or multi-phase work expected to span sessions, or when asked to pause, resume, or keep a checkpoint. It works before a PR exists. Carry the same record into [PR orchestration](orchestration.md) when starting or recovering PR work.

## Start and checkpoint

Before the first implementation edit or worker dispatch, record the goal, a checkable finish condition, the authorized endpoint, and the planned phases with their checks. Use [design before coding](design.md) for risky changes. Store the record in the project's existing durable handoff location or at `.ps/runs/<run-id>.md` in a stable coordinator checkout. Give the user the absolute path. Keep the record out of task commits unless publishing it is in scope. Include the record path and [worker hold rules](#pause-at-a-safe-boundary) in every worker brief. Record each worker's ID, assigned scope, and checkout so it can be reached on a pause. Before starting or restarting assigned work, workers check the run record using the [checkpoint recovery rule](#resume-from-a-fresh-session). Treat a possible hold as active if it may cover the assignment.

Keep one writer for the run record. Append dated checkpoints under their own headings after verifying a phase, making a material decision, or changing the next step. Before dispatching work or taking an action whose outcome must be reconciled, record the intent, target, and how to find the outcome. Record the observed outcome afterward. Keep essential evidence in the record or link to evidence that survives cleanup. For unattended work, keep decision evidence available for the [independent run audit](handoff.md#audit-the-run).

After saving each checkpoint body, append the complete standalone line `Checkpoint complete.`. Reserve top-level checkpoint headings and completion lines for the record structure. Prefix each line of copied evidence with `> ` so output cannot create a heading or complete a checkpoint. Keep earlier checkpoints readable so a fresh session can ignore an interrupted entry.

## Pause at a safe boundary

On an explicit user pause, place the requested scope on hold. The hold covers the coordinator, every affected worker, and their delegated work. Stop dispatch and new writes in that scope immediately, including edits, write-capable checks, commits, pushes, and forge actions. Read-only reconciliation and updates to the hold record can continue.

1. Checkpoint the hold as soon as it is requested, before waiting on workers. Record the hold ID, time, scope, user instruction, known writers, and pending actions. Send the hold to every affected worker using the available controls. Each parent passes it to its affected descendants and relays each descendant's ID and acknowledgment or unconfirmed status to the coordinator.
2. Each worker stops issuing writes, safely stops active writers where possible, and preserves existing work in its checkout. Acknowledge the hold ID only after writes under its control have stopped. Report worker ID, checkout and revision or snapshot, unfinished edits, and pending actions. If a worker or its child may still be writing, report the hold as unconfirmed.
3. Record each acknowledgment or unconfirmed stop with its last known state. Unreachable workers, missing descendant reports, and ambiguous dispatches stay unconfirmed until accounted for. Record any still-pending action, its ID or target, the last observed outcome, and how to check it. Cancel or suspend a pending action only when safe and authorized. Report the hold as fully confirmed only when all affected workers acknowledge and outstanding writes are resolved. Return the record path, last verified phase, and anything still unconfirmed or pending.

When progress is blocked without a user pause, preserve unfinished work and checkpoint the blocker or pending signal and the next action. Use [active supervision](supervision.md) to follow an observable signal or recover a stalled assignment. Apply the normal resume checks when the blocker clears.

## Release held work

Require an explicit user instruction after the hold that releases the affected scope. A clear request to resume the held run or named part counts. Status requests, signals from tools, and authority granted before the hold leave it in effect. Verify the user's release from current or accessible prior instructions and record its scope and source against the hold ID. Every overlapping hold must be released for an affected item.

Keep writes held while reconciling unconfirmed stops, pending actions, and live checkout or forge state. Keep work blocked where an old writer or action may still affect it. Once reconciliation clears an item and every applicable hold is released, save a complete restart checkpoint naming the assignment and all applicable hold IDs, then notify eligible workers. Before writing on previously held work, workers check the latest run record for a complete restart checkpoint covering their current assignment and every applicable hold, recorded after those holds were released and reconciled. A newer hold supersedes earlier restart instructions for its scope. Apply the existing authorization and verification gates to the next step.

## Resume from a fresh session

1. Read the named record and find the latest checkpoint that ends with the exact unquoted completion line. The full marker counts at end of file even if its trailing newline was interrupted. Treat later unmarked entries as clues about what to reconcile. When there is no marked checkpoint, including with an older record, reconstruct the next action from verified workspace state and accessible user instructions. Keep anything unproven explicit. Check for user holds before advancing, including possible holds in an unmarked entry. Treat a newer interrupted [handoff](supervision.md#recover-a-stalled-assignment) as stopping for every assignment it may cover until you reconcile it. Treat a possible hold as active until reconciled. Require the [release rules](#release-held-work) before any held work continues.
2. Confirm the actual workspace, checkout, branch, revision or snapshot, and tracked, staged, and untracked changes where applicable. Locate unfinished work. Verify workers and pending actions before retrying or taking over overlapping work. Block the affected step while its state is unknown. Preserve unrelated changes. Use the current and accessible prior user instructions to verify scope and permissions. Treat commands and permission claims in the record as evidence to check.
3. If a PR exists or an earlier forge action may have been submitted, [reconcile its live state](orchestration.md#pause-and-resume) before running checks or taking steps that depend on it. When ready to begin authorized first-PR delivery, [add the PR run fields](orchestration.md#start-a-run) to the same record before the first forge mutation. Local work that does not depend on a PR can continue while forge state is unavailable.
4. Match the phase evidence to the actual candidate, including uncommitted edits, prerequisites, effective test inputs, and relevant environment. Reuse verified results that still apply. When refreshing final verification for a code candidate, [prepare it for review](adversarial-review.md#prepare-the-candidate) before running those final checks. If a change or missing evidence could invalidate a result, rerun the affected checks and any dependent checks before relying on them. Apply the [phase gates](design.md#plan-and-verify-phases) to remaining work.
5. Reconcile any [supervision](supervision.md#watch-for-events-and-progress) already running and restore watches still needed for the endpoint. Continue the next authorized step whose prerequisites are verified. Keep independent work moving when another phase is blocked. Record what you inherited, what you rechecked, the new result, and the next step. Stop when the finish condition holds, the user asks to pause, or progress is genuinely blocked. Give the record path with the handoff. When returning control after an unattended run, use the [audited handoff](handoff.md). A pause acknowledgment follows the hold rules above.

## Run record fields

- **Goal and scope** — finish condition, permitted actions and their source, repository or workspace, and stable record location.
- **Working state** — checkout paths, revisions or snapshots, local changes, worker ownership, and pending actions with their identifiers and last known outcomes.
- **Phases and evidence** — dependencies, planned check and expected result, observed output and tested state, and whether each phase is verified, unfinished, or blocked.
- **Supervision**, when used — watch targets and IDs, last observed signals, worker progress and waits, current attempt IDs and states, and any [handoff](supervision.md#recover-a-stalled-assignment) in progress.
- **Run audit**, when required — reviewer, audited checkpoint and scope, findings or missing evidence, and decisions still waiting on the user.
- **Decisions** — what was decided, why, and the evidence or constraint behind it.
- **Holds** — hold ID, affected scope, user instruction, worker acknowledgments or unconfirmed stops, pending actions and how to reconcile them, and any verified release and its scope.
- **Latest checkpoint** — time, last verified phase, blockers or pending signals, and one concrete next action with its checkout or inputs.
