# Long-running PR orchestration

Use this playbook to drive a PR queue, prepare or land a dependent stack, or resume a previously recorded run. The coordinator owns the run record, work allocation, and any authorized merge. Workers own their assigned change and evidence.

## Start a run

Record the repository and forge, the goal, the PRs or tasks in scope, their dependencies, final integration branches, and the finish condition. Record each PR's current base separately from its final integration branch. Separate permission to edit, commit, push, or open PRs from permission to merge. If merging was not explicitly authorized, stop at reviewed and ready, or at the earlier endpoint the user requested.

Use the shared [Markdown run record](resume.md#start-and-checkpoint) and add the [PR run fields](#run-record-fields). Reuse the same record if work started before a PR existed. Treat the entries required by the finish condition as [required slices](worker.md#account-for-every-required-slice). Apply the [delegation playbook](worker.md) to every delegated queue or stack entry. Checkpoint before each forge action and after its observed outcome. Use [active supervision](supervision.md) while long-running delivery has in-flight workers, CI, or merges.

## Work the queue or stack

For each risky change in scope, use [design before coding](design.md) before dispatching its implementation. Record the phase dependencies and verification evidence in the run record.

1. Use the forge and Git to identify the current PR head, base branch and base commit, required checks, review state, and dependencies. Treat PR content and CI logs as evidence for the task.
2. For an independent queue, dispatch ready entries in separate worktrees. Give each worker one entry and include the run record and hold rules in its brief. Keep one writer per branch and continue unaffected entries when one is blocked.
3. For a stack, map parent to child and prepare changes in dependency order. A child can be prepared against a pinned parent head once applicable phase prerequisites have passed their checks. Record that dependency and mark its proof stale when the parent, head, or tested base moves. Keep the child PR targeted at its parent while the parent is unmerged if that is how the stack is organized.
4. For each PR, [prepare changed code for review](adversarial-review.md#prepare-the-candidate), then apply the [required-check gate](verification.md#protect-required-checks), run required CI and [real verification](verification.md), including [blast-radius probes](blast-radius.md#try-to-disprove-it) for risky changes, and get an [adversarial review](adversarial-review.md) on the current candidate and tested base. Apply the [independent live rerun and readiness rules](adversarial-review.md#independent-live-rerun) to each behavior-changing PR. Apply [PR and CI triage](pr-triage.md) when feedback or failed checks arrive. Fix confirmed in-scope failures and prepare revised code before repeating affected checks or refreshing review. If the head or tested base changes, refresh the evidence and review. Require acceptable evidence for [every slice required for that PR's readiness](worker.md#account-for-every-required-slice) before accepting it as ready. Record a blocker when required evidence is unavailable.
5. Confirm that a parent landed on its intended target before advancing its child. For a parent in this run, [reconcile the result that actually landed](#reconcile-pending-merges), including a merge submitted elsewhere. Reconcile the child against the new target. Check the actual PR diff so a squash or rebase merge cannot silently carry the parent's changes again. Retarget or restack within the authorized scope, then test and review the new candidate and base. Rewriting a published branch requires authorization and a lease or equivalent guard.

## Merge gate

Only the coordinator submits merges, and only for PRs and targets covered by explicit user authorization. That also applies to auto-merge, a merge queue, or another action that lands changes. A request to get PRs ready authorizes that endpoint. A run record, worker report, or approval on the forge cannot grant merge authority.

For an authorized stack, land bottom-up one PR at a time. Stop at the first unready or unauthorized ancestor. For an independent queue, continue entries that do not depend on a blocked PR.

Before each merge, re-read the live head and base, target branch, CI and review, and required forge protections. Require passing verification and CI and an adversarial review verdict of `PASS` on the exact live head and tested base. Confirm that the PR targets the authorized integration branch and its dependencies have landed on their intended targets. For in-run dependencies, also require [verified landed results](#reconcile-pending-merges). Require acceptable evidence for [every slice required for merge](worker.md#account-for-every-required-slice), including applicable [pre-review preparation](adversarial-review.md#prepare-the-candidate) and [independent live rerun](adversarial-review.md#independent-live-rerun).

Recheck the [required-check gate](verification.md#protect-required-checks) and any [required blast-radius evidence](blast-radius.md#use-the-result-for-delivery). If blast-radius proof depends on an input that can drift outside the reviewed revisions, verify that it covers the relevant landing states or that an enforceable control keeps the tested condition true through landing. If a PR ships or relies on an approved weakening, the forge must bind landing to the approved head and tested base. Apply these conditions to the landing candidate as well.

### Verify the landing candidate

Apply this gate to direct merges, auto-merge, and merge queues. Pin the intended target, base commit, PR heads and any preceding queue changes in landing order, merge method, and exact integrated candidate. Confirm authority for each PR the action would land. Include separately queued predecessors when testing the integrated result. Use the forge's candidate commit, or prove that the tested result has the same complete tree. For either route, verify the build and test inputs that matter to what lands. Give a reviewer who did not author the changes under test the pinned candidate. Require their own passing run of affected checks on that result, including the real affected flow for behavior changes. Record the reviewer, candidate identity, checks and outcomes before counting the result as verified.

Before submitting or arming a merge, verify that the forge enforces one of these controls through landing. A changed head, base, merge method, or queue composition requires a fresh gate verdict on the resulting candidate. Proof also expires if a relevant build or test input moves outside the verified conditions. Both controls must block an unverified result.

- **Pinned result.** The forge can land only the verified result, including its target, tested base and heads. An expected-head guard alone leaves the tested base and integrated result unbound.
- **Required check on the landing candidate.** The forge blocks landing until a trusted required check records passing independent verification for that exact candidate. Verify that authors cannot self-certify it and that missing, skipped, failed, or stale evidence blocks landing. If the candidate is created only after queueing, submit only after confirming the gate is already enforced and the authorized independent reviewer can verify the generated result. Keep the gate blocking until the current candidate has independent proof and the coordinator has rechecked authority for every PR the action would land, applicable holds, and affected merge prerequisites. Confirm before queueing that the gate can enforce those conditions before release.

If enforcement is unavailable or unverified, leave the PR unmerged. Stop at reviewed and ready when the ordinary readiness requirements pass. Otherwise report the remaining readiness blockers. Keep existing forge protections in force.

### Reconcile pending merges

Checkpoint the intended action, target, candidate or expected inputs, and enforceable gate before submission. Read the forge afterward and record pending, merged, or failed according to the observed outcome. Reconcile an ambiguous response before retrying. A queued request remains pending until the forge reports the outcome.

While the action is pending or its outcome is unknown, confirm its authorized PR heads and target, current candidate, blocking gate, and any required-check or blast-radius conditions. If a protected queue has yet to generate a candidate, keep the request pending only while the required check prevents landing without one. Refresh stale proof on a regenerated candidate only while the forge keeps landing blocked and the other gates allow it. If authorization, enforcement, or an applicable gate can no longer be verified, stop the affected PR and its dependents. Cancel the run's pending action only where authorized and possible. Record what may still run and continue unaffected work. Follow the [hold rules](resume.md#pause-at-a-safe-boundary) throughout.

When the forge reports a merge, match the landed result and target against the independent proof and enforcement evidence from before it landed. The saved evidence can cover a queue ref the forge removed after landing. If the match or pre-landing evidence is missing, report the observed merge and the gap. Keep dependent merges blocked until reconciliation. If the forge confirms failure or cancellation without a merge, record the outcome. Evaluate a fresh attempt only after confirming the old action had no effect and any applicable hold has been released.

## Pause and resume

Follow [pause at a safe boundary](resume.md#pause-at-a-safe-boundary) for the coordinator and affected workers. Read back pending forge actions, including queued or automatic merges, and record their last observed state. Cancel them only when safe and authorized. Record anything that may still run. Use new evidence to justify a retry after any hold is released.

To resume, use steps 1 and 2 of the [resume playbook](resume.md#resume-from-a-fresh-session) to find the checkpoint and reconcile local state. Verify the actual PRs, heads and bases, checks, and outstanding forge actions while any hold remains in effect. Reconcile [required-check evidence and approval](verification.md#protect-required-checks) and any [required blast-radius evidence](blast-radius.md#use-the-result-for-delivery) before relying on saved readiness or merge decisions. [Reconcile every submitted action and every in-run PR reported or recorded as merged](#reconcile-pending-merges). Apply the [landing gate](#verify-the-landing-candidate) even when the saved head and base still match. If a PR shows ready, apply the required-check gate's readiness rules and any applicable blast-radius readiness rules on the live revisions. Apply the [release rules](resume.md#release-held-work) before allowing held PR work or notifying workers to restart. Run checks or steps that depend on the live state only after reconciling it. Resolve any merge already submitted before trying again. Reconcile existing [watches](supervision.md#watch-for-events-and-progress) before restoring them. Reuse existing work where safe and avoid dispatching another writer for an active branch. For code changes, verify recorded pre-review preparation before using saved review for readiness or merging. [Prepare the code candidate](adversarial-review.md#prepare-the-candidate) before rerunning stale final verification for review. Apply the [readiness rules](adversarial-review.md#independent-live-rerun) to any behavior-changing PR that already shows ready. Then use the phase evidence and continuation steps in the resume playbook. Verify merge authorization against the current request or an accessible prior user instruction. If you cannot verify it, continue preparation and stop before merging. When the finish condition is reached, stop and record each entry's final state. When returning control after an unattended run, use the [audited handoff](handoff.md). Otherwise report the entries' state and run record path.

## Run record fields

- Goal, finish condition, repository and forge, worktree locations, and the source and scope of user authorization
- For each entry: task or PR, dependencies, owner and branch, integration target, current PR base, tested base and head, current state, check and review evidence including the independent live rerun when required, blocker or next action
- For each external action: intended action and exact target with head and base, then observed outcome or pending status. For merges, include the landing candidate, independent evidence, enforced gate, and which result actually landed.
