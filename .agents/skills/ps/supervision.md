# Supervise a long-running task

Use this playbook when asked to monitor work or while an unattended run has active workers, checks, or external actions that can advance the requested endpoint. Continue from the [run record](resume.md#start-and-checkpoint). The coordinator owns decisions and the record. Any watcher only observes and reports.

## Watch for events and progress

1. Record the finish condition, what to watch, and how to read back the live state. For a PR, pin the forge, repository, PR number, head and base, plus known CI run or merge action IDs. For workers, track the assignment attempt ID, owner and descendant IDs, last verifiable progress, and when to check again. Choose a stall threshold based on comparable work or the current step's expected runtime.
2. Use an available read-only event watcher or a bounded forge wait for CI completion, ref changes, or merge outcomes. Keep a periodic fallback and wake by the next due worker or forge check even if the watcher is still waiting. If events are unavailable, recheck at intervals that suit the expected signal and back off when the forge or agent host is unavailable. Record the watch or next check so a resumed coordinator can adopt an existing watcher or restore a missing one. If the host cannot wake this run after exit, keep watching while active where possible and checkpoint how to resume when it cannot continue.
3. On an event or timed check, read the current record for [holds](resume.md#pause-at-a-safe-boundary) and verify the signal through the live forge, checkout, or worker tools. Treat notifications as prompts to look. Use the live effective CI result tied to the current head or tested merge result and verify a merge landed on the intended target before advancing dependents. Reconcile saved evidence when revisions change. Apply the [merge reconciliation rules](orchestration.md#reconcile-pending-merges) on every readback, including when revisions still match or the forge reports a queued action landed. If the forge is unavailable, record what may still run and confirm the outcome before advancing dependent work. Duplicate or old events leave a current disposition in place unless the readback establishes a change. Have the coordinator apply [PR and CI triage](pr-triage.md) to new feedback or failures from the current candidate.
4. Checkpoint material findings and the next wait or authorized action. Continue unaffected work and recheck the finish condition. Apply the normal [verification and delivery rules](workflow.md#pr-and-handoff) before advancing a PR. During a user hold, follow its write and release rules even when a watcher reports progress. Retire watches for finished work. When no authorized step or usable watch can make progress, record what is blocked, what may still be running, and how to resume. Use the [audited handoff](handoff.md) when returning control after unattended work. For other monitoring requests, report the blocker, any action still running, and how to resume.

## Distinguish a stall from a wait

- **Progressing.** Check for new evidence attributable to the assignment, such as an expected change in its checkout, a verified checkpoint, a completed check, or a test artifact that advances the current step. A generic heartbeat or a worker's status label alone leaves progress unverified.
- **Waiting.** Verify the pending dependency, CI run, merge action, user decision, or hold. Record the signal that ends the wait and check it again when due. Help clear an in-scope dependency where possible. A worker with a valid wait keeps its assignment.
- **Possibly stalled.** When progress is overdue or an error is reported, probe the owner and descendants. Check the actual artifacts and any running tool or forge jobs. An unreachable worker or unavailable observation leaves its state unconfirmed.
- **Stalled.** Confirm a terminal failure that prevents the assignment from continuing, or an overdue assignment whose live probe shows no progress and no valid wait. Record the evidence and start recovery. Treat the stall decision and confirmation that writes have stopped as separate checks.

## Recover a stalled assignment

1. Start a checkpoint naming the stalled assignment ID and marking it stopping. Record the last verified state and pending actions, complete the checkpoint, then tell the owner and descendants to stop if reachable. The stopping state suspends new writes for that attempt and remains in force while reconciling or replacing it. Confirm through acknowledgments and live readback that the previous writer and its descendants, jobs, and pending actions can no longer affect the assignment, or verify an existing host control that prevents those writes. Use the [hold rules](resume.md#pause-at-a-safe-boundary) for any user hold. If a writer or action remains unconfirmed, keep overlapping work blocked and continue independent slices.
2. Reconcile the old checkout, uncommitted work, remote branch, and pending forge actions. Preserve unfinished edits and find the most recent verified point. Verify the current authorization, prerequisites, and any release before transferring ownership. Reuse evidence only where the candidate and inputs still match.
3. Checkpoint a new attempt with a distinct ID and proposed owner before dispatch. Give the replacement a fresh [worker brief](worker.md#worker-brief) pinned to the recovered state and identify the remaining proof. Mark the attempt active in a complete checkpoint only after confirming the new worker's identity and that no competing writer can act. If dispatch is interrupted or ambiguous, reconcile its actual outcome before activating or issuing another assignment. A superseded attempt stays stopped. Resume supervision and [account for the slice](worker.md#account-for-every-required-slice) under its existing completion gates.
